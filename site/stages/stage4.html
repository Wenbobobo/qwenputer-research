从"能跑"到"知道边界"

阶段一复现、阶段二定位、阶段三给创意；阶段四把四件后续事情做实：GPU 路径验证、 H1 记忆实验、memory-disk v0、设备树小原型。核心结论：GPU 快约 40× 但"bit-exact"依赖 kernel； 专用设备只有 2 层/~千个非零权重；memory-disk 能把"记忆"变成可校验、可迁移的文件。

环境：WSL ROCm 7.2.1 + RX 7900 XT 19.96GB + CPU（Ryzen 5700X / 48GB）数据：gpu/、analysis/device/、analysis/memory_disk/、analysis/experiments/h1/

01GPU 路径：43–45 tok/s，与"条件性 bit-exact"

同一份 rv-tiny 权重，从 CPU 搬到 AMD RX 7900 XT（ROCm）后，速度提升约 40 倍，但中间残差的逐位一致性变了——这是一个重要的独立发现。

1.1 速度与正确性

程序生成 tokenGPU 墙钟GPU tok/s与参考 trace 一致
signext443.2 s13.6*✅
memcpy1596.0 s26.6✅
call47410.4 s45.4✅
rv32ui-add50111.1 s45.3✅
c-strops1,07324.5 s43.7✅
c-crc324,16595.9 s43.4✅

* 短程序包含启动开销。CPU 基线 0.7–1.4 tok/s（docs/notes/repro-log.md），GPU 约 40×。显存峰值 4.2 GiB（rv-tiny 4.3GB 权重）。 kernel 走 torch 参考实现（无 flash-linear-attention / causal-conv1d），若安装 fla 还能更快。 7/7 程序 free-running 与参考逐 token 一致（含 4,165 token 的 c-crc32）。

1.2 关键发现：ROCm 上 residual 不是 bit-exact，但 token 仍 exact

检查CPUROCm（7900XT）
signext prefill：118,800 个 cell 中不一致014,192（663 dims），max|d| 1.21e-3
memcpy prefill：422,400 个 cell 中不一致—（CPU 已验证 0）56,272（674 dims），max|d| 1.43e-3
free-running 生成 token完全一致完全一致（包括 4,165 token 的 c-crc32）
解释：同一 checkpoint、同一 dtype（bf16），CPU 的 residual 与 IR 逐位一致；ROCm 上因 kernel 累加顺序不同，中间值出现 ~1e-3 的噪声。 A 进一步定位到 第一个 FFN 的 gate/up 两个 bf16 GEMM 的相消残差（silu、乘积、down GEMM 都逐位一致；换 rocBLAS 环境无效）。 但电路的阈值/边距吸收了噪声，token 输出仍然逐 token 正确——这与作者对 fp32 的观察一致（0 wrong tokens，但非 bit-exact）。 所以"exact in bf16"应更准确地写成：token-exact 在测试程序上成立；dim-bit-exact 依赖后端/内核。需要 residual 级参考时用 CPU 或 Triton 执行器。

检查结果

对照作者 L4 的 ~3,200 tok/s——AMD 7900 XT 上 Triton/HIP graph 路径同样可用，batch 32 甚至更高。Triton 基础 sanity：vector add 559 GB/s、bf16 rowsum 与 torch 一致。

1.4 发布模型（22.3GB）的显存可行性

  • 权重 20.67 GiB（tied embedding/lm_head 占 4.47 GiB），GPU 总 19.96 GiB → 稠密放不下。
  • 去掉 embedding 后 16.51 GiB，理论上可"手动 split"（embedding 放 CPU）；本轮因 H1 实验共用 GPU 未完成该尝试（避免 OOM 影响 H1）。
  • 可行路线：压缩布局（~8 GiB，阶段三权重分析已给出 7.951 GiB 无损格式）+ 稀疏/trim 执行端；或用 HF accelerate offload（慢）。

02H1：90 vs 30 的收益，来自覆盖语义还是介质？

阶段二指出：作者的 90% vs 30% 与"同语义主机工具"无显著差异（p≈0.71）。H1 做一个更直接的消融：让宿主工具变成 append-only、给上下文加时间戳，看结果怎么变。

早期 pilot（n=3 cases/条件，仅作过程记录；正式结果见下方）

Pilot 的初步信号（样本太小，不能当结论）：C1/C2 ≈ 89%，C3 33% 变更题，C4 反而最低（部分失败是命名漂移：模型用 get("city") 而 store 里叫 location）。

⭐ 决定性发现：brevity 变体把"30% 上下文"直接拉到 93–100%。 同一份普通上下文，只加一句 "Answer in one short sentence."：更新题 pooled 56/60=93.3%（C3s，seeds 0–1）、时间戳版 82/82=100%（C1s，seeds 0–2）； 而默认自由回答的 C3 pooled 只有 14/90=15.6%、C1 pooled 42/90=46.7%（lenient 100%）。 也就是说：作者"90 vs 30"的绝大部分差距来自回答格式/评分方式，而不是记忆介质，也不是覆盖语义——上下文模型完全能答对，只是会多嘴提一句旧值。 这与阶段二"与主机工具 p≈0.71"的结论方向一致，但更彻底：连"上下文不会更新"这个前提本身都基本不成立。 （pooled seeds 0–2：C1 strict 42/90=46.7%、lenient 90/90=100%；C3 strict 14/90=15.6%、lenient 48/90=53.3%；C1 vs C3 Fisher p=1.0e-5。）
最终结论（seed0 + pooled + brevity）： 把 90 vs 30 拆成三个因素后，结果很干净：
  1. 覆盖语义是决定性的：同为主机工具，C4（覆盖式 put/get）27/30=90%，C2（append-only）只有 7/30=23%，与上下文基线（30%）同一水平。Fisher 检验差异显著。
  2. 介质不是优势：C4 是纯 Python 主机工具，也拿到 90%，与作者 in-weights store 的 90% 持平——与阶段二"p≈0.71"一致。
  3. 30% 基线还掺了评分器/回答风格的水分：C3 pooled strict 15.6%、lenient 53.3%；C1 pooled strict 46.7%、lenient 100%——模型其实知道新值，只是会把旧值当历史再提一句，被 strict 规则判错。加上 brevity 后 C3s 93.3%、C1s 100%。
所以作者"90 vs 30"的正确拆解是：覆盖式工具语义（+短回答）贡献了主要差距，权重内介质没有可测优势，上下文基线被 strict 评分额外压低。 这也解释了为什么阶段二用 host 工具对照时 p≈0.71：介质差异不显著，但覆盖 vs append-only 的差异是真实的。

attribution 细节（B 的诚实拆解）：C4 的 27/30 里，只有 9/30 是"旧值被存下又被覆盖"（9/9 正确）；另外 18/30 是旧值从未被存（18/18 正确），因为 C4 只在 73/120 个会话里调用了 put。 而 C2 存了 112/120 个会话，26/30 里新旧值同时在 memory 里，只有 3/26 答对（答案把两个值都列出来）。所以"90%"里同时包含"模型少存 → 问题变简单"和"覆盖机制有效"两种效应；条件化到"新旧都在"时，覆盖 9/9 vs append-only 3/26 仍然支持覆盖是关键。

03memory-disk v0：把"记忆"变成可校验文件

阶段三 D 证明快照很小但绑定编译；v0 把它工程化：指纹、校验、迁移、以及防住"长名字静默覆盖"。

3.1 API

fp = fingerprint(model_dir)     # sha256(config/chipformer/tokenizer + store 配置 + 版本)
save(snapshot, path, fp, journal=None)   # .npz body + sidecar header（QPUMEM01, checksum, created_at）
load(path, expected_fp=None, force=False) # 指纹不符 -> FingerprintMismatch
verify(path)                               # magic/checksum/header
replay_into_reference_store(journal)       # 逻辑内容跨 seed 重放
NameGuard.check(name) / put_checked(name,text)  # 拦截 6-token 键冲突

04设备树：2 层、~千个非零权重的专用设备

如果 RV32 是"通用 CPU"，那么固定形状的小算法可以编译成"外设"：层数与权重少两三个数量级，token 成本也更低。

设备层dims/headsFFN units非零权重每 op token精确性
ADD8（8+8→9 bit）237 / 182899365,536/65,536 IR；HF 0/40 错
SORT4（4×8-bit 稳定排序）266 / 14373,87683,508 记录 / 14,032 预测 0 错；HF 0/160 错
DADD（十进制逐位大数加）214 / 11791,4542n+1（4 位=9，12+12=25）11,039 记录 0 错；HF 0/1,619 错
RV32 核（参照）11–122,679 / 9942,0121,040,5951.3–1.8/指令；calc 254–684riscv-tests 全绿

4.1 三个有信息量的发现

  • 第二层是 I/O 约定的代价：算术本身 1 层就够；但输入 token 的 code 必须提前一子层清零（bf16 不能在同一层里精确加 −e 与 ±KAPPA）。在宿主模型里可与宿主的 exit 共享这一层。
  • 串行设备需要 record-start token：DADD 第一版没有起始 token，进位跨记录泄漏（5,553 错误）；加 G 复位后 exact。
  • 合并几乎免费：每个设备最多 1 head / 403 units；4B 模型每子层余量 16 heads / 9,216 units（最满子层已用 8,149）→ 估计可并行塞进现有 chip 层，0 额外层。
适用边界：固定形状纯函数（add/compare/小排序/查表/位运算）、状态只有几位的逐位运算（大数加减/比较/乘一行）、高频且想省掉 RV32 的 200–250 token dispatch 的场景。 数据相关循环（gcd/pow/div/解析）、大内存、宽单个 token 操作数、以及大量低频小操作，仍应留在 RV32。

05结论与下一步

问题阶段四给出的答案
GPU 能不能跑？能，rv-tiny 43–45 tok/s（CPU 的 ~40×），全部测试程序 token-exact；但 dim-bit-exact 依赖后端，ROCm 有 ~1e-3 残差。
90 vs 30 是不是介质优势？H1 结果（见第 02 节）：待填。
记忆能不能变成文件？能：memory-disk v0 40/40 测试通过，指纹校验 + journal 迁移 + NameGuard；但根因（6-token 键）仍需电路层修复。
专用设备值得吗？值得：2 层 / ~1K–4K 非零 / 每 op 3–25 token；可并行塞进现有层，RV32 作为通用回退。
下一步优先级：① 用压缩布局（~8GiB）在 7900XT 上跑发布模型的 list/put/get（现在 GPU 已验证速度）；② 把 H1 推广到 n=90 + LongMemEval 语义对照（H5）；③ 把 ADD8/SORT4 设备合进 chip 层，验证"设备树"端到端；④ 修复 6-token 名字键（扩到 8+ token 或显式冲突协议）。
