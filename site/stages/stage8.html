优先级候选结论
Top 1fp32 chip（局部化默认候选）+0.65GB、−7~13% 速度换长序列 lock 3/12→0/12；建议只对 chip 敏感子层 fp32，不做全模型 fp32
Top 2H5 语义路由 + exact get + SafeStoreRecall@5 87%（LongMemEval）、exact get 45 token vs RAG 12,140；价值来自语义入口+精确审计，不是 in-weights 介质本身
Top 3设备树合并原型优先 SORT4/ADD8/DADD；2 层、千级非零、IR exact、小 270–1150×
Kill list：默认全 fp32、CPU-GPU 混合执行、NF4/无保护 INT8、通用 regex/大排序设备、跨模型共享 chip 层、"in-weights 天然更快"叙事、以 Recall@1 为产品指标。
不倒退 gate：CPU bit-identical；GPU token-level + head_mismatch=0 + lock_error=None；回归用例集（put/get、长序列 1/2/5、fp32/bf16 对照）每次发布前跑一遍。

IR check=True：ADD8(255+1)、SORT4([255,0,127,127])、DADD(999+1) 的 private output code 与独立设备一致；CPU emit 成功（SORT4/DADD）。结论：0 额外层，slots 仍在布局容量内。

生产级阻塞

  • 新 token family 与 RV namespace 冲突：需要稳定 namespace、tokenizer 扩展、约 3,193 个 embedding rows；
  • RV、store、器件之间需要互斥 owner/exit dispatcher；器件运行期间冻结 RV counters/heads/capture/store；
  • code.clear 必须早于统一 exit；必须共享 host 的 ONE/ballast（用 active detector 替代 ONE 会导致 bf16 精度失败，实测 −3.37e15 级权重）。

下一步：ADD8-only → rv-tiny 端到端原型，再接 text bridge 的 RV core。

06结论与 Stage 9 规划

Stage 8 结论：
  1. 发布链路打通：每个阶段报告都能以同一流程上线 GitHub Pages；
  2. 正确性优先配置明确：fp32 chip + no-FLA（长序列 0/12 lock divergence，put/get 正确）；
  3. 速度优先候选：bf16 + selective FLA（Hi 14.59 tok/s，长序列待验证）；
  4. 设备树合并 IR 可行：0 额外层、slots 1899/2029，下一步做 ADD8-only rv-tiny 闭环；
  5. H5 两阶段检索可行：Recall@5 96%、CPU 路由 11ms、exact get 0.5ms。

Stage 9 候选（按 ROI）

  • ADD8-only rv-tiny 端到端原型：真实权重 merge + tokenizer/namespace + owner/exit dispatcher，验收 = 设备计算 token-level 正确且 RV32 回退可用；
  • H5 reader 集成：4B reader 上跑 top-1/3/5 vs RAG 四组对照，加低分拒答与索引版本门禁；
  • fp32 chip 局部化：只 fp32 敏感子层（chip attention/qkv/alpha/beta/exit），把 +0.65GB 与速度代价压到最小；
  • 速度 >20 tok/s：native int8 GEMV、tied embedding 量化、causal_conv1d Triton 短卷积（按风险逐个评估）；
  • memory-disk v1：把 trim runtime + SafeStore + journal 打包成可用记忆盘 API。
