把 22.3GB 塞进 20GB，然后快 18 倍

用户问：这个模型有量化版吗？7900 XT 的 16/8/4-bit 哪个最有性价比？怎么迁移到 W4A8/W4A4？我们做了硬件微基准、生态调研、bnb 量化适配与无损 trim 运行时； 最终答案不是"换精度"，而是 去零填充（trim，无损）+ 装回被漏掉的 flash-linear-attention 内核：put 从 73.6s → 4.1s（16.8 tok/s），get 39.8s → 4.0s（13.6 tok/s），显存 13.15GB 全上卡，chip 电路 head mismatch 0。

环境：WSL ROCm 7.2.1 + RX 7900 XT 19.96GB + torch 2.9.1证据：docs/notes/stage6-*.md、gpu/quant/、gpu/trim/、gpu/kernels/

01问题与结论先行

问题答案
有量化版本吗？Filesystem 没有任何量化版；唯一相关是 liodon-ai 的初代 CHIP-8 FP8（结构不同）。base Qwen3.5-4B 的 FP8/GGUF/AWQ 不能套到 merged 模型（44 层 / hidden 4608 / 词表 484800 / GDN 算子）。
7900 XT 哪种精度最划算？BF16 计算最划算（实测 75.8–78.3 TFLOPS）。INT8 kernel 只有 70 TOPS（不比 BF16 快）；FP8 无原生 WMMA（Triton 降级 FP16）；INT4 有原生 WMMA，专用 decode GEMV 实测 1.4–1.5×——但整体仍受带宽与内核限制。
该怎么量化？只能量化 Qwen 12–43 层（chip 0–11 必须 bf16 精确）；且必须先处理 mute 列（mu=2732 ≈ −15.06），否则 bnb8 直接乱码。修正后 bnb8 全 GPU 正确，但只有 1.1–2.4 tok/s。
那性能怎么解决？无损 Trim + FLA：Qwen 只读 2560+mu 列、只写前 2560 维 → 裁掉 61.8% 零后 13.15GB 全进显存；再用 flash-linear-attention 融合 GDN 内核替代 reference PyTorch → put 16.84 tok/s、get 13.62 tok/s（基线 0.98 / 0.4–1.1）。
一句话：这张卡上量化的价值是"省显存"（bnb8 11.5GB），不是"省算力"；真正的速度来自 去掉乘零的带宽浪费（trim） 与 换掉 reference GDN 内核（FLA）。两者都不损失 chip 电路精确性（head_mismatch 0、lock None），trim 在 CPU 对拍上甚至 bit-identical（max_abs_logit_diff 0.0）。

W4A8 / W4A4 路径（研究结论）

  • W4A16（bnb NF4）：显存最省（8.6GB）但质量崩（"!!!!!!!!!!!!"），当前直接替换不可用。
  • W4A8：packed W4 → 解包到 INT8 → 原生 INT8 WMMA；理论上 ROCm 可行，需要自定义 Triton/HIP kernel + 校准；官方工具链（Quark/AITER）重心在 CDNA，RDNA3 需自研。
  • W4A4：需要 IU4 WMMA packing、per-group scales、激活量化校准（QuaRot/SpinQuant 类），RDNA3 上无现成算子，属于长期方向。
  • 从实测看：decode 是带宽受限，所以 W4 的收益上限 ≈ 权重字节比（~4×），但会被 dequant 开销吃掉一部分；先做 trim（去掉 61.8% 零）比换精度收益更确定。

04三条实测路线

4.1 bnb8 量化（S5）——"显存成功，速度失败"

  • 失败根因：merged Qwen 的 mute 列（输入 2732，≈ −1024/√4608 = −15.06）主导 per-row 缩放，把正常权重压没 → 乱码。
  • 修复 PreserveColumns：chip 维（≥2560）非零列拆成 bf16 侧投影（<1MB），量化矩阵里置零；文本恢复。
  • 结果：全 GPU（无 offload）、11.49GB 峰值、load 105–145s；put/get 正确（69+3 / 80+3 tokens）、head 0；但 Hi 2.38 tok/s、put 1.10 tok/s、get 1.08 tok/s。
  • NF4：8.64GB、解码 9.26 tok/s（FLA 的功劳），但输出 "!!!!!!!!!!!!" → 不可用。

4.2 FLA 融合内核（S7）——"白捡 1.5–3.3×"

  • 装回 flash-linear-attention 0.6.0 后，transformers 不再对 GDN 走 reference PyTorch（只剩 causal_conv1d 两个 fallback）。
  • bnb8+FLA：Hi 2.71、put 1.71（1.55×）、get 2.44（3.3×）tok/s，transcripts 与基线逐字一致、head 0。
  • repro 本来就为 FLA 设计（gpucheck.py 测 FLA 下的 RV core；core.py:492 的 one-hot 设计避免 FLA chunk 的 fp32 残差）→ chip exactness 保持。

4.3 无损 Trim（S6）——"去掉乘零"

  • Qwen 层只读 2560+mu 列、只写前 2560 维；裁掉后 Qwen numel 6.42G→3.57G；248 个矩阵逐一验证只丢精确零。
  • CPU 对拍：plain_hi 15 个位置 bit-identical（max_abs_logit_diff 0.0）、argmax 15/15。
  • GPU：13.15GB 峰值、load 60–150s；no-FLA 时 Hi 4.47–6.96、put 6.79、get 9.0 tok/s。
  • head-trim（lm_head 只保留 text-vocab 2600 维）：Hi 10.15 tok/s（no-FLA），显存 14.8GB。

怎么理解 16.84 tok/s：72 tokens / 4.10s = 17.6 ms/token。trim 后每 token 需读 Qwen 7.1GB + lm_head 4.47GB ≈ 11.6GB，除以 17.6ms ≈ 660 GB/s——正好是 7900 XT 的有效带宽。也就是说 trim+FLA 已经跑在带宽上限；再要快只能减小每 token 字节数（head-trim/int8 lm_head/W4）或增大 batch。
最终推荐：默认用 trim + FLA（13.15GB；put 16.84 / get 13.62 tok/s）——显存占用与速度最平衡；短问答/交互场景用 trim + head-trim + FLA（Hi 12.39 tok/s，延迟最低，代价是 14.7GB 显存）。 两者 put/get 全部正确（head mismatch 0、lock None），trim 在 CPU 对拍上 bit-identical（max_abs_logit_diff 0.0）。相比 Stage 5：put 73.6s → 4.1s（18×），get 39.8s → 3.9s（10×），Hi 7.7s → 0.73s（10.5×）。
🔧 精确性结论再修正（22:15）：后续对照发现，即使完全屏蔽 FLA（纯 torch fallback），gpucheck 在 7900 XT 上同样失败，残差与 FLA 时完全相同（−5.96e-8，0 wrong tokens）；FLA 0.5.2（作者验证版本）亦然。 说明 AMD gfx1100/ROCm 的 bf16 GEMM 本身就不是 bit-exact，作者的 bit-exact 记录是 NVIDIA L4 专属结论。因此在 AMD 上"精确"应表述为：CPU 上 bit-identical；GPU 上 token-level 正确（head_mismatch 0、lock None）。FLA 不引入新的错误类别，只是把 1-ULP 级数值差异暴露在门禁里。下面的"FLA 非 bit-exact"改为"AMD GPU 整体非 bit-exact"。
⚠ FLA 精确性门禁（21:40 实测，已按上方修正理解）：python -m chipformer.rv.gpucheck --decode 在 FLA 0.6.0 下对 signext / call / memcpy / rv32ui-lb / rv32ui-sh 五个测试的 prefill+decode 全部 MISMATCH，差异 6e-8 ~ 9.4e-7（fp32 1 ULP 级）。 这证明 FLA 对 chip 层不是 bit-exact；put/get 之所以正确，是电路对 1e-7 级扰动有容错，而非精确性恢复。 因此最终推荐分两档：① 精确默认 = trim（无 FLA）：put 10.16s / get 6.00s / Hi 2.0s（6.8–9 tok/s），文本与基线逐字一致、CPU bit-identical； ② 速度模式 = trim + FLA（可选 head-trim）：put 4.1s / get 4.0s / Hi 0.73–2.0s（13.6–16.8 tok/s），功能正确但 chip 非 bit-exact，需按负载验证。

注：bnb8 的 9.26 tok/s NF4 数字无效（输出非 EOS 的乱码，速度不可用）。FLA 安装时间点（20:10:56）之后启动的运行都含 FLA，跨配置比较需注意。head-trim 与 trim+FLA 的 put 差异（4.38 vs 4.10s）在噪声范围内。

后续修正（Stage 7 复测）：本页 trim（no-FLA）的 6.79/9.00 tok/s 是在同机 CPU 检查进程干扰下测的；GPU 独占、CPU 空闲时复测为 13.48–14.71 tok/s。因此 trim 的绝对速度以 13+ tok/s 为准，FLA 相对增益从"2–4×"修正为约 1.2×（full FLA put 16.84 vs 13.60）；"660GB/s 带宽上限"的结论仍成立（full FLA put 4.10s ≈ 660GB/s）。

06限制与下一步

  • FLA 是全局开关：它同时作用于 chip 层；本项目的 put/get 与 CPU 对拍都通过，但建议把 python -m chipformer.rv.gpucheck --decode（FLA 下）作为回归门禁再接受。
  • causal_conv1d 仍走 reference：可源码编译 ROCm 版或用 FLA 的 Triton short-conv，预计还有 5–15% 空间。
  • 剩余带宽大头是 lm_head（4.47GB/token）：head-trim 只保留 text-vocab 2600 维可降到 ~2.5GB；再叠 int8 可到 ~1.3GB（需要按行 chunked dequant，避免瞬时 2.5GB 峰值）。
  • W4A8/W4A4：需自研 Triton/HIP 内核与校准，暂不作近期目标；先用 trim+head-trim 把带宽打满。
  • 量化结论（负结果）：bnb8 保留作为"显存 ≤12GB 时的保底"，不推荐作为性能路径；NF4 当前不可用。
