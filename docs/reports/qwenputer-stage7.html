精确性的边界，和记忆的最后一臂

阶段七回答了两个悬而未决的问题："能不能既快又 bit-exact？"——不能，因为 7900 XT/ROCm 的 bf16 GEMM 本身就不是 bit-exact（屏蔽 FLA 也一样，作者结论是 NVIDIA L4 专属）； "in-weights 记忆到底有没有优势？"——H1 缺失的 in-weights 一臂补上了：changed 10/10 = 100%，与 host 覆盖式工具同档 → 覆盖语义是关键，介质没有可测优势。

环境：WSL ROCm 7.2.1 + RX 7900 XT + trim runtime证据：docs/notes/stage7-*.md、gpu/out/*.json、analysis/experiments/h1_inweights/

01AMD 精确性边界：不是 FLA 的错

我们曾以为 FLA 破坏了 chip 层 bit-exact。三组对照推翻了它。

配置gpucheck --decode（7900 XT）wrong tokens
FLA 0.6.0（全量）MISMATCH，残留 −5.96e-8 ~ 9.4e-70
屏蔽 FLA（纯 torch fallback）同样 MISMATCH，残差完全相同0
FLA 0.5.2（作者验证版本）同样失败（677 dims 不 bit-exact）0
CPU（纯 torch）通过；max_abs_logit_diff 0.0、argmax 15/15 + 66/660
结论：AMD gfx1100/ROCm 的 bf16 GEMM 归约顺序本身就产生 1-ULP 级差异，与 FLA 无关；作者"bit-exact"是 NVIDIA L4 的验证结论。 在 AMD 上正确的表述只能是：CPU 路径 bit-identical；GPU 路径 token-level 正确（head_mismatch 0、lock_error None）。
长序列的代价：H1 in-weights 的长历史（数百 token）中出现 3 次历史 calc lock divergence（cases 1/2/5）——问题轮本身全部干净，说明短上下文完全可用，但长序列的电路数值漂移是 AMD GPU 的已知限制。
01b 长序列的正解（Stage 8 预研已出正面结果）：把 12 个 chip 层改成 fp32 计算、Qwen/embedding/lm_head 保持 bf16（TRIM_FP32_CHIP=1，参数 +0.65GB）。严格 paired 对照（同一 harness、同一天）：bf16 chip 3/12 lock divergences（recall-1/s1、recall-2/s1、recall-5/s2）→ fp32 chip 0/12；bf16 在原失败点提前分叉（chip tokens 仅 25），fp32 完整执行 calc（4077/2841/2704 chip tokens）且 lock=None、head 全 0。速度代价很小：put 16.88→15.72、fresh-get 15.52→14.69、Hi warm 16.56→18.87 tok/s，峰值 13.3→13.94GB。这是目前 AMD 上"长序列电路正确性"最有效的修复方向（详细见 docs/notes/stage8-fp32chip.md）。

用发布版 Qwenputer 自己的文件系统（RvChat 的 put/get store、MEM_SYSTEM）在同样的 4 会话事实集上跑 10 个 case（no-FLA trim，GPU）。

3.1 这个结果说明什么

  • changed 100%：in-weights store 的覆盖式写入与 host 覆盖式工具同档，远高于 append-only（40%）和上下文（30%）——再次确认"覆盖语义"是决定性因素。
  • 介质没有可测优势：host 工具用 Python 也能到 80–90%，in-weights 并没有显著更高；不构成等价性，也不构成"权重内介质更优"。
  • 事实题 85% 的失分是任务侧：模型偶尔没执行 put（unsaved facts）、重复 get 到答案预算上限；不是存储丢失。
  • 长序列 caveat：3 次历史 calc lock divergence（cases 1/2/5），lock-clean 子集 changed 7/7、facts 11/14、all 18/21；30 个问题轮 lock 全干净、head mismatch 0。
  • 诚实性：raw store_after 显示有 tuple-key 解码 bug（已修），原始 store 诊断不可靠；transcript 显示只有 4 个 changed case 在 session 结束时仍留旧值、1 个以不同 key 保留旧值——因此结论按"可观测行为"陈述，不做等价性声明。

04int8 head 与 ROCm 调优（进行中）

tied embedding/lm_head 是每 token 的最后一块带宽大头（~4.47GB）。CPU 侧检查全部通过，但 GPU 实测是负结果。

配置（同一串行 session，GPU 独占）Hiputget峰值正确性
base trim（无 int8、无 env）13.48 cold / 18.73 warm13.60（8.25s wall）14.71（7.46s wall）13.22GB✅ head 0
int8 head（TRIM_INT8_HEAD=1）11.21 cold / 8.73 warm11.7311.9613.86GBput/get 逐 token 相同；Hi 首 token 分叉为 list tool call
+ TORCH_BLAS_PREFER_HIPBLASLT=110.58 cold / 16.47 warm（−21.5%）——13.39GB✅
+ TunableOp 校准（2 iter，含 108s 校准）4.58 cold / 13.17 warm——17.47GB✅ 无收益
结论：int8 head 不划算。compact head 确实只有 675MB（vs 4.47GB），40 个 chip 列保持精确 bf16，circuit-only 探针 logits max_diff 0 / chip argmax 相同（434286）、Qwen-only 探针 argmax 也一致；但 GPU 上：
  • 保留 bf16 embedding + 单存 int8 lm_head 会多占 +0.65GB，不会省 2GB；
  • chunked dequant 的开销抵消了带宽收益 → Hi 13.48→11.21、put 13.60→11.73、get 14.71→11.96（−14%~−19%）；
  • Hi 的首个 token 与 BF16 基线分叉（变成 list tool call），put/get 则逐 token 相同——不能宣称全场景一致；
  • HIPBLASLt 偏好 −21.5%（10.58）；TunableOp 冷端 4.58（含 108s 校准）、峰值 17.47GB，无收益。
下一步要真正省带宽，应把共享的 tied 张量本身量化（embedding 行 int8 + chip 维稀疏 bf16），或把 lm_head 的 4.47GB 按 2560+40 维裁剪（head-trim 已做）并配合更粗粒度的 dequant。

06结论与下一步

阶段七的三个定论：
  1. 精确性边界：AMD GPU bf16 非 bit-exact（与 FLA 无关）；CPU 是唯一 bit-identical 参考；GPU 以 token-level 正确为验收标准。
  2. 速度：trim no-FLA 6.8–9 / selective 12.2–12.4 / full-FLA 13.6–16.8 tok/s；int8 head 若成功可再 +20–30%。
  3. 记忆：in-weights changed 100%，与 host 覆盖式同档 → 覆盖语义是关键，介质无优势；"90 vs 30"的差距主要是覆盖语义 + 回答格式，不是权重内存储。

下一步（Stage 8 候选）

  • fp32 chip 层（paired 已验证）：chip 层 fp32 + Qwen bf16，同一 harness 下 bf16 3/12 → fp32 0/12 lock divergence，速度 put 15.72 / get 14.69 / Hi warm 18.87 tok/s、峰值 13.94GB；下一步扩到更多输入并做 gpucheck fp32 门禁。
  • int8 head 落地：把 lm_head 4.47GB/token 降到 ~1.3GB，目标 >20 tok/s；同时评估 embedding 行 int8 + chip 维稀疏 bf16。
  • causal_conv1d 替代：FLA Triton 短卷积，预计 +8–15%。
  • memory-disk v1：把 trim runtime、SafeStore、in-weights store 组合成可用记忆盘；用 selective FLA 12 tok/s 做交互。
  • H1 整合：把 in-weights 结果与 host/context 四条合并进阶段二/四报告，作为"记忆介质"问题的最终答案。
